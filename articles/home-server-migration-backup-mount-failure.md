自宅サーバの移設は深夜0時16分に完了しました。専用機側は動いており、その時点で目立つ異常はありませんでした。ところが翌日、バックアップの最後の成功が移設前日の12時35分で止まっていることに気づきました。以降の3回はすべて「そこはマウントポイントではない」というエラーで失敗していたのです。

移設と同じ操作で、共有ストレージを指すマウントが構成から外れていたと推定しています。今回はこの1日で起きたことと、そこから決めた暫定ルールをまとめます。

## 正しく失敗したバックアップと、静かに壊れた別の処理

失敗したバックアップは、安全弁が働いていました。マウントされていないローカルディスクへ書き込む前に処理を止め、空のバックアップで既存の正常な世代を上書きすることもありませんでした。困る失敗ではありますが、壊れ方としては正しいものです。行き先が確認できないなら止まる、という設計が機能していました。

移設中に走った回は途中で中断され、転送用の作業ディレクトリだけが残っていました。半端な成果物がバックアップとして確定する事態は避けられています。

一方、別の処理には同じ安全弁がありませんでした。マウントが外れる前日から、未マウントのパスへ約1.3MBをローカルに書き続けていたのです。プロセスは動いているように見えますが、本来の共有ストレージには届いていません。同じ「マウント外れ」でも、検出のされ方は正反対でした。安全弁のある処理は「失敗して止まる」、ない処理は「動いているつもりで行き先を失う」。後者は必要になる日まで被害が表面化しません。

移設後の確認で数えるべきなのは、新しい環境で起動した処理の数ではありません。バックアップや退避、世代管理のように、止まっても当日は困らない処理が、以前どおり最後まで完了しているかどうかです。

## 応急の退避と恒久対応を分けて考える

発見した当日のうちに、新しい機から旧環境のファイルを読み、別筐体へ退避アーカイブを1本作成しました。サイズは9.2GiB、圧縮検査を通し、469,930エントリの一覧と主要ディレクトリの存在も確認しています。「アーカイブを作成できた」だけでは退避完了とは言えません。読めること、想定した規模であること、必要な場所が含まれることまでを確認して、初めて応急対応の完了としました。

恒久対応では、旧環境のマウントを直す選択肢は取りませんでした。旧環境は畳む予定であり、そこを直しても移設後に捨てる資産を増やすだけになるためです。代わりに、同じ仕事を新環境が引き取る形にしました。応急対応は「今あるデータを安全な場所へ置くこと」、恒久対応は「次回から同じ仕事をどこで担うか決めること」であり、この二つを混ぜると復旧できた安心感だけが残り、引き継ぎ漏れを見落とします。

## 移設期間中は、消さない側に倒す

移設期間中は世代削除の既定を無効にしました。保持数を超えた世代はログに列挙するだけで、自動削除はしません。削除は取り消せない操作であり、移設直後はどの処理がどこまで引き継がれ、どこに欠損があるかの判断材料が不足しています。この期間だけ削除を止めておけば、容量の問題は残りますが、復旧の選択肢を失うことは避けられます。

## 教訓・チェックリスト

- 移設完了の判定を「新環境が起動した」だけに置かない。旧環境側で止まった処理は誰も観測していない可能性がある
- バックアップ・退避・世代管理など、止まっても当日は困らない処理こそ、移設直後に個別で成功ログを確認する
- マウント外れを検知する仕組みがない処理は、書き込み先のディスク使用量やinode数の推移で代用監視できないか点検する
- 退避アーカイブは「作成できた」で終わらせず、読めること・規模・必要なディレクトリの存在まで確認する
- 恒久対応と応急対応を同じタスクにしない。旧環境を直すか新環境に引き取らせるかは、旧環境の今後の扱いを踏まえて決める
- 移設期間中は削除系の既定を無効にし、超過分はログ列挙のみに留める

移設は移した先ではなく、移した元を静かに壊すことがあります。今回出せる結論はここまでで、何も起きない種類の処理が止まったことをどう当日に検知するかは、まだ解けていません。
