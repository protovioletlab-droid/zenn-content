## この記事について

自宅ラボでAIエージェント(Claude Code / Codex CLI)を常時運用しています。その稼働テレメトリをOpenTelemetryで集約する基盤を約1ヶ月回した記録です。

先にこの記事の主張を書きます。**計装デモを締切ドリブンで作るのではなく、観測基盤を先に常時稼働させて実事件を溜める。** 書く時点でネタは揃っています。「計装してみた」の1歩先、入れた計装で実際に何が捕れて、そこから閾値や設計をどう決め直したかまでが本題です。約束を3つ:

- 事件・数値・グラフはすべて実環境の実測。演出用に作った障害は1つもありません
- アラート閾値・メモリ上限・OOM序列は、その実測から逆算した値だけを載せます
- きれいな図の裏で起きた「引き継ぎ忘れ」「誤帰属」「偽陽性」のような格好悪い話も、観測ログに残っているのでそのまま書きます

なお、ホスト名・unit名・jobラベルは公開用に仮名化しています(スクリーンショット内の表示名も同様に置換。構成・数値・時刻は実物のままです)。

1ヶ月で捕まえた事件は次の4つです。

1. GPUメトリクスの11日間の沈黙(と「期待された沈黙」の設計)
2. ホスト移設の継ぎ目が時系列にそのまま刻まれた話(と、移設が静かに落としたOTel環境変数)
3. swap枯渇級のメモリ圧イベント(PSI 86%)の観測と原因unitの特定
4. 観測パイプライン自体の障害(exporter失敗・trace欠落の偽陽性・quotaゲートの読み方バグ)

![1ヶ月の実事件4件のまとめ](/images/otel-contest/fig-a4-casefile.png)

事件の合間に、AIエージェントをOTelで観測する時の具体的な設定・メトリクスカタログ・検知器の作り方も書いていきます。

## 環境と構成

環境は自宅のProxmoxクラスタ+監視用Dockerホスト+ゲームPC兼用のエージェント実行ホストです。エージェントは複数ノードで動いていて、対話セッションだけでなく、記事生成パイプラインや定期メンテナンスのようなcron駆動の無人実行も含みます。「人間が見ていない時間帯にAIエージェントが働いている」環境なので、観測がないと本当に何も分かりません。

![観測基盤の全体構成: 3つのプロデューサ→OTel Collector→Prometheus/Tempo→Grafana・夜間チェック・LLMステュワード](/images/otel-contest/fig-a0-architecture.png)

collectorはOTLP(gRPC :4317 / HTTP :4318)で受け、メトリクスはPrometheusがscrapeできる形(:8889)で露出、トレースはTempoへ流します。既存のPrometheus/Grafanaスタックがあるなら、composeにcollectorとTempoを足すだけで受け皿は完成します。

1点だけ最初にやっておいてよかったのは、**collector自身のテレメトリ(self-metrics)を初日からPrometheusに入れた**ことです。新しめのcollectorでは `service.telemetry.metrics.readers` 配下にpull型のPrometheus exporterを定義すると、:8888で自身のメトリクスを露出できます。`otelcol_receiver_accepted_metric_points`(受け入れた点数)、`otelcol_receiver_refused_metric_points`(拒否した点数)、`otelcol_exporter_queue_size`(送信キュー長)あたりが見えないcollectorはブラックボックスで、後述の事件4はこれが無いと検知できませんでした。

規模感: Prometheus全体で約2万系列(実測19,814)、うちAIエージェント関連の系列は直近24時間で数百〜1,100系列程度が動いています。自宅ラボとしては小さくない量ですが、Prometheus 1台で余裕の範囲です。

## Claude Codeの計装は環境変数だけ

この構成の肝は、プロデューサ側の計装がほぼ「設定だけ」で済むことです。Claude Codeは環境変数でOTLPテレメトリを吐けます。

```bash
CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_METRICS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_EXPORTER_OTLP_ENDPOINT=http://<collector>:4318
OTEL_RESOURCE_ATTRIBUTES=host.name=<ホスト名>
```

これで届くメトリクスのうち、1ヶ月使って「実際に見る価値があった」ものを挙げます。

| メトリクス | 何が分かるか |
|---|---|
| `claude_code_session_count_total` | セッション開始数。無人cron実行の生死確認の一次指標 |
| `claude_code_token_usage_tokens_total` | トークン消費。`type`(input/output/cache系)と`model`のラベル付き |
| `claude_code_cost_usage_USD_total` | API換算のコスト推定。定額プランでも負荷の相対比較に使える |
| `claude_code_active_time_seconds_total` | 実際に動いていた時間。セッション数より稼働実態に近い |
| `claude_code_lines_of_code_count_total` | 書き換えた行数。「今日エージェントは何をしたか」の粗い答え |
| `claude_code_commit_count_total` | commit数。自律作業の産出量 |
| `claude_code_code_edit_tool_decision_total` | 編集ツールの許可/拒否。permission設計の見直し材料 |

ハマりどころを1つ。リソース属性の `host.name` は、Prometheusに入ると `host_name` ラベルになります(ドットがアンダースコアに正規化される)。PromQLやアラート条件は必ず正規化後の名前に合わせてください。「設定した属性名でクエリして0件」は誰もが一度踏む穴で、うちでは後述の移設事件の検知条件がこれに依存していたので、属性名の不一致がそのまま検知漏れになるところでした。

トークン集計はこんな形で使っています。

```promql
# ホスト×モデル別のトークン消費(24h)
sum by (host_name, model) (increase(claude_code_token_usage_tokens_total[24h]))

# 無人実行ノードの生存確認: セッションが今日始まっているか
sum by (host_name) (increase(claude_code_session_count_total[24h]))
```

## 蓄積の仕組み①: 夜間tickと「産出物の有無」

観測基盤は入れただけでは事件を捕まえてくれません。うちでは毎晩21:30にcronの検査スクリプト(夜間tick)が走り、観測ログ(`observations.jsonl`)へ1行追記します。1行はこんな形です(実物から抜粋・整形)。

```json
{"ts": "2026-07-25T21:30:01+09:00", "ok": true,
 "total_series": 19814, "ai_series_24h": 91,
 "pipeline_trace_search_hits": 1, "queue": "0/1000",
 "producers": {"gpu-main GPU exporter": {"silence_state": "active"}, "...": "..."},
 "notes": ["gpu-sub GPU exporter 無信号(10m) — 停止中の想定沈黙: 電源OFF運用"]}
```

tickが見ているのは収集の生死ではなく「何を捕まえたか」です。

- **プロデューサ別の無信号**: 系列の最終サンプル時刻ベース。プロセスの死活ではなく「データが着地しているか」を見る
- **collectorの受信拒否・失敗、exporterキューの飽和**: パイプライン自体の異常
- **期待しているパイプラインtraceの欠落**: 無人実行が計装ごと沈黙していないか
- 異常時のみチャット通知(事件はそのまま記事素材になる)

ここで得た運用原則を先に書いておきます。**監視の観測面は「プロセスが生きているか」ではなく「産出物が出ているか」に置く。** cronが正常終了していてもJSONLが増えていなければそれは異常です。逆にプロセス監視が全部緑でも、産出物が止まっていれば何かが壊れています。AIエージェントの無人運用ではこれが特に効きます。エージェントは「正常終了したが何もしていない」という壊れ方をするからです。

tickは異常を見つけると、観測ログとは別にイベントファイル(`otel.jsonl`)へwarn/criticalのイベントを積みます。これが次のステュワードの起動条件になります。さらに「人間が着手すべき作業候補」は第3のファイル(work-order候補のJSONL)へ分離しました。観測の記録・機械向けのイベント・人間向けのタスク候補は読者が違うので、1つのファイルに混ぜると全員にとって読みにくくなります。

### 事件簿のスキーマで決めたこと

観測ログの各行は「定期観測の行」と「事件の行」の2種類です。定期観測の行は毎晩必ず書く(異常が無くても書く)。これで「記録が無い日=tick自体が死んだ日」が機械的に分かります。監視の監視を別途作るより、まず記録を無条件化する方が安上がりです。

事件の行は `incident`(1行の結論)と `evidence`(構造化した根拠)のペアにします。ここで効くのは、**evidenceに「測った値」だけでなく「切り分けに使った値」を残す**ことです。事件1のevidenceに `collector_up: 1` が入っているのは、当時「collectorは容疑者から外した」根拠を将来の自分に残すためです。文章の障害報告は結論だけが残りがちですが、JSONのevidenceは切り分けの過程ごと固定できます。

もう1つ、時刻は必ずタイムゾーン付き(この環境はJST)で書きます。cronの発火時刻・Prometheusのサンプル時刻・カーネルカウンタの読み取り時刻を突き合わせる作業は、ゾーンが曖昧な記録が1つ混ざるだけで信頼できなくなります。「ゾーンを確定してから比較する」は地味ですが、事件2のような「08:10に終わり19:40に始まる」系の議論の前提です。

## 蓄積の仕組み②: 6時間毎のLLMステュワード

たまったイベントの深掘りは、6時間毎にLLM(Codex CLI)へ委任しています。「Prometheusをクエリして仮説を立てて観測ログに追記する」までを無人でやる係です。ただしLLM実行は重いので、無条件には走らせません。3段ゲートを通します。

1. **イベントゲート**: 新しいwarn/criticalイベントがある時だけ起動(なければSKIP)
2. **quotaゲート**: CLIの利用残量スナップショットを読み、残量が閾値未満ならSKIP。読めない時もSKIP(fail-closed)
3. **debounce**: 直近に走っていたらSKIP

実際の1回の実行記録(実物)はこの規模です:

```json
{"steward": {"model": "gpt-5.6-sol", "effort": "low",
             "elapsed_seconds": 96, "tokens_used": 42493, "events_consumed": 8}}
```

96秒・4.2万トークンでイベント8件を消化。深掘りの品質は人間のSREには及びませんが、「翌朝人間が見る時に、一次調査が終わっている」だけで十分に元が取れます。

サンドボックスについても書いておきます。当初この係は無サンドボックス(全権)で動かしていましたが、途中でworkspace書き込み限定+承認なし実行+**ネットワークだけ明示的に開放**する構成へ切り替えました。workspace限定サンドボックスは既定で外向きネットワークを閉じるため、そのままだとPrometheusにクエリできません。「LLMに権限を渡しすぎない」と「観測クエリは打てる」の両立は、この明示開放の一手間で成立します。全権LLMをcronで回すのは、動いてしまうだけに一番危ない構成です。

プロンプト設計で1つだけ強調したいのは、**書き込み先の分離**です。ステュワードには観測ログ(JSONL)を「読み取り入力」として渡し、追記はさせません。JSONLに追記するのは夜間tickだけで、ステュワードの分析結果はプロジェクト文書の観測ログ節という別の場所に書かせます。同じファイルに機械とLLMの両方が書く構成にすると、フォーマット崩れの発生源が2つになり、壊れた時にどちらを疑うかから調査が始まってしまいます。書き手は1ファイル1者。これはLLMに限らない原則ですが、出力形式が揺れうるLLMでは特に効きます。

またイベントには「クローズ条件」を明文で持たせています(例:「解消を確認した」「期待された沈黙として受理した」など)。LLMに深掘りを委任する時、終わり方を定義しないと、同じイベントを毎回掘り直すか、勝手に完了扱いにするかのどちらかに倒れます。

そしてこのquotaゲート自身がバグっていた話は、事件4で書きます。

## 事件1: GPUメトリクス、11日間の沈黙

7/17の夜間tickが「GPU系列が3晩連続でゼロ」を検知しました。観測ログの実物(抜粋)です。

```json
{"incident": "both GPU exporter series absent for three nightly ticks",
 "evidence": {"gpu_series_24h": 0,
              "last_sample_jst": "2026-07-14T09:33:57+09:00",
              "hosts_with_same_last_sample": 2,
              "collector_up": 1,
              "receiver_failed_refused_24h_increase": 0}}
```

このevidenceの並びが、切り分けの手順そのものです。

- `collector_up: 1` — 受け皿は生きている
- `receiver_failed_refused_24h_increase: 0` — 受信失敗も拒否も増えていない
- `hosts_with_same_last_sample: 2` — 2ホストが**同時刻に**止まっている

つまりcollectorやネットワークではなく、**送る側が同一原因で止まった**。

原因は障害ではありませんでした。7/14にローカルLLMの常用をやめてGPUワークロードを意図的に休止した際、GPUメトリクスの採取スクリプトも一緒に止まっていたのです(さらに直後の環境移設の移行対象からも漏れていました)。人間は全員「止めた」と知っていた。しかし**監視にはそれを誰も伝えていなかった**。だから夜間tickは、3晩連続の無信号を粛々と事件として扱いました。採取を再開したのは7/25 22:35。ギャップは11日間です。

![GPUメトリクスの11日間の沈黙](/images/otel-contest/fig-a1-gpu-gap.png)

Grafanaの実画面ではこう見えます(retentionの都合で7/17以降の窓。左半分の空白が沈黙、7/25に系列が復活):

![Grafana実画面: GPUダッシュボード。7/25まで無信号、以降復帰](/images/otel-contest/shot-grafana-gpu.png)

再開時に決めたルールが2つあります。1つ目、**メトリクス名・単位・hostラベルは一字も変えない**。`gpu_utilization_percent` / `gpu_memory_used_bytes` / `gpu_temperature_celsius` / `gpu_power_watts` など7系列には停止前の履歴があり、名前を「今風に」直すと過去と比較できない別系列になります。既存系列がある環境での再計装は、命名の美学より連続性です。

2つ目が本題の「沈黙の分類」です。この事件の本当の教訓は「意図的な停止は、監視に教えない限り事件になる」でした。加えてうちには電源を入れっぱなしにしないGPUホストもあり(使う時だけon→off運用)、素朴な無信号アラートだと**平常運転まで毎晩エラーに見えます**。そこでtickの無信号判定を3値にしました。

- `silence`(異常): 動いているはずのプロデューサが沈黙している
- `expected_down`(平常): 電源off運用ホストの沈黙。系列は「電源投入中だけ生える」のが正しい
- `suspended`(平常): 退役・休止・移設で意図的に止めたプロデューサ。理由文字列つきで台帳管理(この事件の直接の産物です)

tickのコードでは、監視対象のプロデューサ一覧と「意図的に止めた」台帳を分けて持ちます(実物から抜粋)。

```python
SUSPENDED_PRODUCERS = {
    "agent-lxc Claude telemetry":
        "旧ホストを参照専用へ静音化(2026-07-25)。沈黙は期待状態",
}
# 判定側: 台帳にあれば expected_suspended として理由ごとnotesに残す
if name in SUSPENDED_PRODUCERS:
    rec["producers"][name]["silence_state"] = "expected_suspended"
```

ポイントは、期待された沈黙を「アラート抑制」で握りつぶすのではなく、**理由つきで毎晩記録し続ける**ことです。後から観測ログを読むと「この沈黙は当時から想定内だった」が一次資料で確認できます。さらに低頻度プロデューサ(週数回しか動かないノード)は「24時間無信号だが7日窓では実績あり」を正常休止と判定する2窓方式にしました。沈黙には期待された沈黙がある。これを分けないアラートは、3日でオオカミ少年になります。

採取経路の話も添えておきます。GPUメトリクスの採取スクリプトは、常時稼働ホストのGPUは**ローカルで**nvidia-smiを読み、電源off運用ホストは到達できた時だけSSH越しに読みます。移設前の旧構成では常時稼働ホストのGPUもSSH越しに読んでいたのですが、移設後は採取スクリプトがそのホスト自身で動くようになったため、ネットワーク経由をやめました。SSHの採取経路は「相手が落ちている」が平常なので、失敗をエラーに数えず `expected_down` に落とします。実際、電源off運用ホストを検証のために起動した際は、SSH疎通→GPU 12点の送信→Prometheus着地まで一気に確認でき、そのまま電源を落として平常(=沈黙)に戻りました。**系列は「電源投入中だけ生える」ことそのものが正しい状態**という監視は、3値分類なしには書けません。

可視化はダッシュボード3枚に落ち着きました。全体俯瞰(ホストとエージェント稼働)、GPU専用(利用率・VRAM・温度・電力)、そして収集健全性(collector self-metricsとコンテナリソース)です。枚数を絞ったのは、夜間tickが異常検知を担っているからです。ダッシュボードは「アラートが鳴った後に開く道具」と割り切ると、パネルを増やす誘惑から自由になれます。

## 事件2: ホスト移設の継ぎ目と、静かに消えたOTel環境変数

7/25にエージェントの実行環境をLXCから物理ホストへ移設しました。`claude_code_*` を `host_name` で集計すると、移設がそのまま時系列に刻まれています。旧ホストの系列が08:10で終わり、新ホストの系列が19:40から始まる。

![ホスト移設の継ぎ目](/images/otel-contest/fig-a2-migration-seam.png)

移設時のテレメトリ設定で守ったのは、新ホストの `OTEL_RESOURCE_ATTRIBUTES` に**恒久的なホスト名を明示する**ことです。既定のホスト名に任せると、コンテナ名や一時的なhostnameが `host_name` に入り、ダッシュボードやアラートの条件が全部壊れます。検収も「設定した」ではなく、最小セッションを1本流して `claude_code_session_count_total{host_name="<新ホスト>"}` がPrometheusに着地するまで見ました。

きれいな話はここまでです。実際には移設が1つ、観測を静かに壊していました。

7/27の昼のチェックで、記事生成パイプラインのtraceが**7/25 08:00を最後に消えている**ことに気づきます。観測ログの実物では:

```json
{"incident": "aria-blog-pipeline trace absent since 7/25 08:00 —
  cause identified: migration dropped OTel env, NOT a pipeline failure",
 "evidence": {"last_trace_jst": "2026-07-25T08:00:01",
              "episode_20260726": {"result": "done", "wp_post": 774}}}
```

evidenceが示す通り、パイプライン自体は正常で、7/26のエピソードは完走してWordPress投稿(post 774)まで済んでいます。落ちたのは処理ではなく**計装**でした。移設で作り直したcron定義に `OTEL_EXPORTER_OTLP_ENDPOINT` を引き継ぎ忘れていたのです。アプリは環境変数が無ければ「計装なしで正常動作」するので、誰も何も気づきません。

復旧はcronへ環境変数を戻し、**本物の実行経路**(本番の仮想環境+実際のtelemetryモジュール)でselftest traceを流してTempo着地を確認して完了としました。ここの教訓は2つです。

- **移設のチェックリストに「テレメトリ設定」を独立項目で入れる。** アプリが動くことと観測が動くことは別の検収項目。環境変数渡しの計装は、この「静かに消える」性質とセットです。
- **「traceが無い」を検知する側を作っておく。** 処理が成功し続ける限り、計装の死は自然には発覚しません。うちはtickの「期待trace欠落」検査が2日で気づかせてくれました。

## 事件3: swap枯渇級メモリ圧の1ヶ月

このラボで7月最大の事件はメモリ圧でした。AIエージェントの実行基盤は、複数の常駐サーバとバッチが同居するメモリ大食い環境です。時系列で3幕あります。

**第1幕(7/17): 観測ギャップの発見。** 発端は障害ではなく「エージェント実行環境(割当80GiB)のメモリ容量系列がそもそも取れていない」ことへの気づきでした。node_exporter+cgroup読み取りを整備して初めて実態が見えます: cgroupのfile cacheが41.3GiB、ブート以降のピークRSSは71.6GiB。さらに累積カウンタを読むと `swap_fail_events` が約246万回、`memory_high_events` が約226万回。**症状として表面化する前から、圧力はカーネルのカウンタに積もっていた**わけです。「モニタリングを入れた日に初めて、ずっと前からあった問題が見える」は観測あるあるですが、累積カウンタはその場で過去を語ってくれる貴重な証人です。

第1幕には失敗談があります。当初、コンテナ階層の `memory.high` イベントを親cgroupから読んでいて、**子cgroupで起きたイベントを親のせいに誤帰属**していました。cgroup v2の `memory.events` は配下サブツリーのイベントを含み、自分自身のイベントだけを見るには `memory.events.local` を読む必要があります。修正後は、意図的に小さな `MemoryHigh` を与えたテストunitで「localだけが増える」ことを回帰テストにして固定しました。cgroup v2でメモリイベントを監視する予定がある人は、この2ファイルの違いを踏む前に知っておくと得です。

**第2幕(7/22): 本番の圧力バースト。** 13:44にアラート開始、14:20に全回復。ピーク時の実測は:

- 実行環境全体のメモリ 64.2GiB(うち匿名ページ31.5GiB)、swap 8GiBを使い切り
- memory PSI(some, avg60)ピーク **86.82%**
- swap失敗カウンタの増分 約2.26億
- OOM kill 0件(ギリギリ耐えた)

Grafanaの実画面がこの週の全てを語ってくれます。右上の`agent memory`でRSSの推移、`agent swap`で7/22のswap 8GiB到達、`agent PSI avg60`で86%のスパイク、`agent memory events`でカーネルイベントの爆発が、同じ時間軸に並びます:

![Grafana実画面: メモリ事件の1週間(7/17-7/24)。swapスパイク・PSI 86%・memory events](/images/otel-contest/shot-grafana-memory.png)

ここで第1幕の整備が効きます。unit別のcgroup計測があったので「ホストが苦しい」で終わらず、**原因unitはCodexのアプリサーバ(ピーク25.7GiB、swap 7.96GiB)**と特定できました。ホスト使用率のグラフをどれだけ拡大しても、この結論は出てきません。攻めるべき設定(該当unitのメモリ上限とOOM優先順位)も自動的に決まりました。

事件後の恒久対策も観測が決めました。常駐unitにはsystemdの `MemoryHigh` / `MemoryMax` で宣言的な上限を与え、`OOMScoreAdjust` で「メモリが本当に尽きた時に誰から死ぬか」の序列を明示しました。序列の設計方針は単純で、対話セッションより先に補助的な常駐が死ぬこと。上限値は勘ではなく、第1幕・第2幕で取れた実測ピーク(unit別のcurrent/peak)から逆算しています。**上限とOOM序列は、実測が無いとただの願望になります。**

**第3幕: PSIを主役にする。** この事件の間、平常時のPSIは0%、バースト中だけ86%でした。PSI(Pressure Stall Information)は「メモリ使用率が高い」と「プロセスが実際にメモリ待ちで止まっている」を区別できる指標です。使用率90%でも快適なホストはいくらでもあり(file cacheが賢く使われているだけ)、逆に使用率70%でもswapスラッシングで死んでいるホストもあります。アラート閾値を使用率からPSIへ寄せると、偽陽性と偽陰性が同時に減ります。この経験から、メモリ監視の推奨セットは `MemAvailable` / swap絶対量 / PSI / major fault / OOM killの5点に落ち着きました。

## 事件4: 観測パイプライン自身も観測対象

最後の事件群は、観測する側の障害です。3件あります。

**collectorのexporter失敗(7/4)。** 稼働初日の23:21、collectorの `otlp_http/metrics` exporterの失敗を、collector自身のメトリクス(`otelcol_exporter_*`)で検知しました。監視スタックの構成変更に伴うもので翌日解消。初日からself-metricsを入れておいた効果が、初日に出ました。平常時の収集健全性ダッシュボードはこの形です(受信数・拒否0・キュー0/1000・collector自身のメモリ):

![Grafana実画面: 収集健全性ダッシュボード(直近7日)](/images/otel-contest/shot-grafana-health.png)

**trace欠落アラートの偽陽性(7/10〜7/13)。** 「パイプラインtrace欠落」アラートが繰り返し発火し、調べると**Tempoの検索窓の指定が曖昧**なことによる偽陽性でした。検索開始・終了時刻を明示せずに投げていたため、境界付近で「あるのに見つからない」が起きていた。観測ログには `resolved as recurrent search-window false positive` という行が3回並んでいます。3回同じ結論を書いた時点で「これは事件ではなく検知器のバグ」と認定し、検索窓を明示24時間に固定して収束しました。**検知器そのものも観測とレビューの対象**であり、同じ偽陽性を2回解消したら、それは検知器側の修正チケットです。

**quotaゲートの読み方バグ(7/25)。** ステュワードのquotaゲートが「残量スナップショットの最終行だけ」を読んでいたため、スナップショット採取が一時的に失敗している40分間(直近60件中エラー4件、18:07〜18:37に集中)にtickが当たると、実際には残量十分なのに無用なSKIPをしていました。最初は「収集側が壊れた」と誤診しましたが、採取関数を直接叩くと正常。**壊れていたのは消費側の読み方**でした。修正は「鮮度窓(90分)の中を新しい順に遡り、最初に読めたスナップショットを採用。窓内に1つも無ければ従来通りSKIP」。fail-closedの性格は保ったまま、断続的な採取失敗に耐えるようになりました。検証は実データ(RUN判定・週次残量62%)に加え、合成データで「最新4件エラー→5件目で回復」「窓内全滅→SKIP」「窓外のみ→SKIP」の3ケースを固定しています。

おまけとして、物理層の落とし穴も1つ。ノードのhwmon監視を広げた際、あるマザーボード(DeskMeet B660)のセンサーチップ(NCT6798)が**未結線の入力を-1℃や100℃超のあり得ない値として露出**していることが分かりました。実在する2つの基板センサー・CPU coretemp・NVMe温度・結線済みファン2基だけを残し、残りはnode_exporterの `--collector.hwmon.sensor-exclude` で除外。「取れる値を全部取る」は、存在しないセンサーの亡霊まで取り込みます。

## 生データの保全 — retentionは締切より短い

執筆時に1つ危ないことに気づきました。この環境のPrometheusはretention 15日で回しており、**7/14のGPU停止エッジは7/29頃、7/17のメモリ事件の周辺データは8/1頃に窓から消えます**。つまり「後でゆっくり書こう」と思っていると、記事の図が引き直せなくなる。事件簿(JSONL)には結論とevidenceが残りますが、グラフを描くための生系列は残りません。

そこで執筆に先立って、記事の図に使う系列を `query_range` の生JSONとしてエクスポートしました。窓は2段構えです。

- 全景用: 事件を含む2週間、step 5m(ギャップや継ぎ目の俯瞰)
- 拡大用: 事件週(7/12〜7/18)、step 1m(バーストの立ち上がりを見る)

各ファイルにはクエリ式・step・窓・取得時刻をmetaとして同梱し、一覧はmanifest(47ファイル、全てに系列あり)で固定しました。エクスポート時の落とし穴は前述の通りで、複数メトリクスを `or` で束ねると `__name__` を無視した集合演算で系列が潰れるため、メトリクス毎に個別にクエリします。

汎用的な教訓にすると: **「観測データの寿命」と「そのデータを使う予定日」を一度比べておく**。障害報告・監査・記事、何であれ、根拠のグラフが必要になる日はretentionの外にあるかもしれません。

## これから始める人への最短手順

同じ構成を作るなら、順序はこれが最短だと思います。

1. 既存のPrometheus/Grafana環境にotel-collectorとTempoを足す(composeに2サービス)。collectorはOTLP受け→Prometheus向け露出+Tempo転送だけの最小構成で開始
2. **collector self-metricsを同時に有効化**し、Prometheusのscrape対象に入れる(後回しにすると事件4系が見えない)
3. Claude Code等のエージェントに環境変数5つを配る。`host.name` は恒久名を明示
4. 最小セッションを流し、`host_name` ラベル付きで系列が着地するまでを検収とする(「設定した」で終えない)
5. 夜間チェックを1本書く。最初は「エージェント系列の24時間内の有無」と「collectorの受信失敗増分」の2項目で十分。結果は毎晩1行JSONで追記
6. 沈黙の3値分類(silence / expected_down / suspended)を最初から入れる。後付けすると偽アラートの記憶で信頼が先に死にます
7. 事件が起きたら `incident` + `evidence` の行を残す。ここまでで、この記事と同じ蓄積ループが回り始めます

LLMステュワードのような自動深掘りは、イベントが実際に溜まり始めてからで遅くありません。ゲート(イベント有無・quota・debounce)を先に設計してから委任する、の順序だけ守れば安全に足せます。

## この構成の運用コスト

最後に、この基盤を維持するコストを正直に書きます。

- **金銭**: 追加ゼロです。collectorとTempoは既存の監視用Dockerホストへの相乗りで、SaaSは使っていません(商用SaaSを併用する話は[別記事](https://zenn.dev/chemy_pvl/articles/splunk-o11y-asymmetric-overlay)に分けました)。
- **常駐プロセス**: collectorとTempoだけ。夜間tick・ステュワード・GPU採取はすべてcronの単発実行で、常駐ワーカーを増やしていません。自宅ラボでは「便利のために立てた常駐」が一番のメモリ泥棒になるので、batch優先は意識的な選択です。
- **LLMコスト**: ステュワードは1回96秒・約4.2万トークン(実測)。ただしイベントゲートのおかげで、平穏な日は起動すらしません。実際の観測ログでも大半の日はイベントなしのSKIPです。quotaゲートがあるので、エージェント本業の残量を観測係が食い潰すこともありません。
- **人間の時間**: 毎朝、夜間tickの1行と(あれば)ステュワードの深掘りを読むのに数分。事件が起きた時だけ、evidenceを起点に調査します。切り分けの一次資料が揃った状態から始められるので、この1ヶ月の事件対応はどれも短時間で済みました。

観測基盤自体の障害(事件4)も含めて、この規模のラボなら「片手間で維持できて、事件の時だけ本気を出す」運用が現実に成立します。

## まとめ: 蓄積ループの設計原則

1ヶ月回して残った原則を並べます。

1. **基盤先行・締切は収穫日。** 事件は予約できない。常時稼働だけが実物のネタを供給する。この記事の4事件のうち3つは向こうから来ました。残る1つ(事件1)は自分たちの運用変更を監視に伝えていなかったことで「事件になった」もので、これも常時稼働していなければ気づけません。
2. **1件クローズ=1ビート。** 発見→記録→検証→解消→記録、を観測ログ(JSONL)に積む。evidenceを構造化して残すと、後から読む時に切り分けの手順ごと再生できます。
3. **沈黙を分類する。** silence / expected_down / suspended。期待された沈黙は握りつぶさず、理由つきで記録し続ける。
4. **産出物の有無を観測面にする。** プロセス健全性は根拠にならない。特にAIエージェントは「正常終了したが何もしていない」壊れ方をする。
5. **計装の死を検知する側を作る。** アプリが正常な限り、消えた環境変数には誰も気づかない。期待traceの欠落検査は安い保険です。
6. **検知器も観測対象。** 同じ偽陽性を2回解消したら検知器を直す。quotaゲートのような運用ガードも例外ではない。
7. **既存系列の連続性は命名の美学に優先する。** 再計装で名前を変えると過去が消える。
8. **生データの寿命に注意。** Prometheusのretention(この環境は15日)は締切より短いことがあります。記事の図に使う系列は `query_range` の生JSONで先に保全しました。1つ注意: 複数のメトリクスを `or` で束ねてエクスポートすると、集合演算が `__name__` を無視して系列が潰れます。メトリクス毎に個別クエリが安全です。
9. **検証はするが捏造はしない。** 「プラットフォームが実異常を捕捉できるか」の確認は検証。事件そのものを作るのは禁止。この線引きを最初に決めておくと、素材の信頼性が守られます。

観測基盤は「入れたら終わり」ではなく、事件を捕まえて初めて元が取れます。そして自宅ラボ程度の規模でも、1ヶ月あれば事件は向こうから来てくれます。AIエージェントを無人で働かせているなら、なおさらです。人間のいない時間帯に起きたことは、テレメトリでしか再生できません。この1ヶ月で言えば、GPUの11日間の沈黙も、移設で消えた環境変数も、深夜のメモリバーストも、発見したのは全部cronと時系列データベースでした。次のシーズンは、この事件簿の上に「事件を減らす」改善を積んでいきます。
